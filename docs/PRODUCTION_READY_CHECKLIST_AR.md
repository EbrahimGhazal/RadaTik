# قائمة جاهزية RadaTik للإنتاج

هذه القائمة تُستخدم قبل النشر إلى بيئة الإنتاج وبعده لضمان تشغيل آمن ومستقر.

## 1) ما قبل النشر (قبل 24 ساعة إلى قبل ساعة)

- التأكد من نجاح البناء والاختبارات:
  - `dotnet build RadaTik/RadaTik.csproj -c Release`
  - `dotnet test RadaTik.Tests/RadaTik.Tests.csproj`
- التحقق من إعدادات الإنتاج:
  - `ConnectionStrings:MyDBConnection`
  - `RADATIK_BOOTSTRAP_ADMIN_PASSWORD` (فقط إذا كانت هناك حاجة لإجراء bootstrap)
  - التأكد أن `RADATIK_INSECURE_HTTP` = **false** في الإنتاج (إلا في حالة خاصة ومدروسة)
- مراجعة الهجرات وقاعدة البيانات:
  - مراجعة الهجرات المعلقة وتأثيرها.
  - أخذ نسخة احتياطية من قاعدة البيانات قبل النشر.
- التحقق من الخدمات الخارجية:
  - اتصال SQL Server من الخادم.
  - اتصال MikroTik API من الخادم.
- التحقق من الملفات الثابتة:
  - وجود بناء الواجهة الأمامية داخل `wwwroot/app` ضمن حزمة الإصدار.

## 2) أثناء النشر (وقت T0)

- إرسال إشعار نافذة النشر لفريق العمليات.
- نشر الحزمة إلى بيئة الهدف.
- تنفيذ فحص سريع مباشر:
  - `GET /health` يرجع `200`.
  - تسجيل الدخول يعمل (مدير النظام + مدير الشركة).
  - لوحات التحكم والصفحات الأساسية تعمل بدون أخطاء خادم.

## 3) التحقق بعد النشر (أول 15 دقيقة)

- التحقق من التدفقات الأساسية:
  - إضافة مشترك عبر الـ wizard تعمل.
  - معاينة/استيراد مشتركين من MikroTik تعمل.
  - عمليات المحفظة والفوترة تُسجَّل بشكل صحيح.
- التحقق من صحة البيانات:
  - السجلات الجديدة في `Clients` و`NetworkWalletTransactions` وجداول الفواتير صحيحة.
  - لا يوجد تكرار غير صحيح للمشتركين ضمن نطاق الشركة.
- التحقق السريع من UX/Accessibility:
  - تبديل القوائم الجانبية بلوحة المفاتيح (Enter/Space) يعمل.
  - رسائل التنبيه تظهر وتغلق بشكل صحيح.
  - مؤشر التركيز واضح في الحقول الأساسية.

## 4) المراقبة (أول 24 ساعة)

- متابعة السجلات ومعدل الأخطاء كل 1-2 ساعة:
  - `Unhandled exceptions`
  - أخطاء اتصال MikroTik
  - أخطاء timeout/deadlock في قاعدة البيانات
- متابعة الأداء:
  - زمن استجابة نقاط API الحرجة (إضافة/استيراد مشترك).
  - استقرار خدمات الخلفية.
- متابعة مؤشرات السلامة التشغيلية:
  - فشل عمليات الفوترة.
  - تغيّرات غير متوقعة في أرصدة المحافظ.
  - فشل تدفقات الطلبات/الموافقات.

## 5) خطة التراجع (Rollback) عند مشكلة حرجة

- إعادة نشر آخر نسخة مستقرة من التطبيق.
- إذا لزم: تنفيذ خطة تراجع قاعدة البيانات المعتمدة أو استعادة النسخة الاحتياطية.
- إعادة فحص سريع:
  - `/health`
  - تسجيل الدخول
  - تدفق عمل أساسي واحد على الأقل
- توثيق حادثة مختصر يشمل:
  - سبب الإطلاق،
  - نطاق التأثير،
  - وقت التراجع،
  - الإجراء التصحيحي التالي.

## 6) اعتماد الإصدار النهائي

يتم اعتماد الإصدار فقط عند تحقق ما يلي:

- البناء والاختبارات ناجحة.
- `health` مستقر.
- التدفقات الأساسية تم اختبارها بنجاح.
- لا توجد تنبيهات حرجة خلال أول 24 ساعة.
- اعتماد فريق العمليات موثق.

## 7) بوابة قرار Go/No-Go (سريعة)

استخدم هذه البوابة كقرار نهائي خلال دقيقتين قبل النشر:

- `GO` فقط إذا تحققت جميع النقاط:
  - البناء والاختبارات ناجحة على نفس نسخة النشر.
  - النسخة الاحتياطية لقاعدة البيانات أُخذت وتم التحقق منها.
  - خطة التراجع جاهزة ومسؤول التراجع محدد.
  - `health` يعمل بعد النشر على بيئة الهدف.
  - تدفق عمل أساسي واحد على الأقل نجح في smoke test.
- `NO-GO` إذا تحقق أي مما يلي:
  - تأثير هجرات غير واضح.
  - وجود عطل إنتاجي حرج (P1/P2) غير محلول.
  - عدم توفر نسخة احتياطية أو عدم تحديد مسؤول التراجع.
  - فشل فحص `health` أو فحص تسجيل الدخول.

## 8) نموذج اعتماد الإصدار (يُملأ قبل النشر)

استخدم النموذج التالي كسجل رسمي لكل عملية نشر إنتاجي:

```text
معرف الإصدار:
تاريخ/وقت الإصدار (UTC):
مسؤول الإصدار:
مسؤول التراجع:

Commit/Tag:
البيئة:

حالة البناء: PASS / FAIL
حالة الاختبارات: PASS / FAIL
النسخة الاحتياطية لقاعدة البيانات مؤكدة: YES / NO
تأثير الهجرات تمت مراجعته: YES / NO
حزمة التراجع جاهزة: YES / NO

فحص Smoke (/health): PASS / FAIL
فحص Smoke (تسجيل الدخول): PASS / FAIL
فحص Smoke (تدفق أساسي): PASS / FAIL

قرار Go/No-Go: GO / NO-GO
صاحب القرار:
وقت القرار (UTC):

ملاحظات:
```
